# Proposed rider API contract

**Status: historical/general design proposals, with accepted contracts now owned
by the backend.** Account and Settings references identify their existing native
consumers. The completed core operations source at `1d785aa` has its own executable
OpenAPI and [integration plan/source review](../plans/native-operations/README.md).
Its exact routes, string money, versions, pagination and command semantics take
precedence over generic examples below. Do not implement accepted operations from
this proposal table or duplicate the owner's schema. Source availability does not
establish Azure, Flutter or physical-device acceptance.

Use `/api/v1` JSON endpoints in the existing Laravel app. Existing Inertia
responses, web session forms, and public masked tracking are not substitutes
for an authenticated rider API. Reuse shared policies, validation, and services.

## Common conventions to freeze first

| Topic | Historical/general proposal; not the accepted core operations schema |
|---|---|
| Transport | HTTPS in release; `Accept: application/json`; UTF-8 JSON except multipart proof |
| Native auth | `Authorization: Bearer <per-device-token>` on authorized first-party requests only |
| IDs | Opaque strings in JSON, even if storage uses integers; scoped parent/child lookup |
| Order status | Canonical uppercase commercial codes plus terminal `CANCELLED`; adapter explicitly maps existing storage values |
| Assignment phase/stage | Separate documented lowercase codes, e.g. `pickup` / `final_mile`; not commercial statuses |
| Money | `{ "currency": "PHP", "minor_units": 125050 }` means PHP 1,250.50; integer centavos, no float calculation |
| Timestamps | Server-generated UTC ISO 8601 with `Z`; display Asia/Manila; server filters local-day history correctly |
| Scheduling dates | Validated `YYYY-MM-DD` only for authorized schedulers; riders cannot schedule retry |
| Collections | `data`, `links`, `meta`; stable explicit sort, default 20 and maximum 50 records per page |
| Null/unknown | `null` means unavailable/not applicable; preserve unknown read statuses, deny unsupported actions, never silently default |
| Versioning | Additive v1 evolution; explicit capability flags; incompatible required changes need a new version or coordinated compatibility window |
| Correlation | Safe `X-Request-Id` per attempt, validated/generated by server; never a credential or proof of idempotency |
| Mutation safety | `Idempotency-Key` per user intent; server ownership/scope/locks/source-state validation still required |

These are project decisions awaiting agreement, not Laravel default behavior.
The backend owner must choose actual limits/expiry/codes before the first slice
is accepted. Record them in the executable contract and keep this document aligned.

## Routes by purpose

| Method and path under `/api/v1` | Purpose and boundary |
|---|---|
| `POST /auth/tokens` | Rate-limited courier login; device label, existing credentials, no client-selected role/approval |
| `DELETE /auth/tokens/current` | Revoke the current native token; idempotent logout result |
| `GET /rider/me` | Own identity, holding/restriction/placement/duty, server capabilities and configured evidence limits |
| `PATCH /rider/duty` | Set own desired boolean duty explicitly; cannot clear restriction or placement gates |
| `GET /rider/pickup-jobs` | Eligible available work and capacity context; scoped minimal seller preview |
| `POST /rider/pickup-jobs/{job}/claim` | Atomic pickup claim; no rider/hub/company IDs chosen by client |
| `GET /rider/tasks?phase=pickup|final_mile` | Own active assignments and permitted next actions |
| `GET /rider/tasks/{task}` | Fresh scoped detail, next stop, task phase/stage and evidence requirements |
| `POST /rider/tasks/{task}/release` | Gated pre-custody claim release with allowlisted reason; not available until recovery rules exist |
| `POST /rider/tasks/{task}/pickup` | Matching submitted waybill and seller handoff evidence; pickup assignment only |
| `POST /rider/tasks/{task}/depart` | Assigned final-mile waybill scan-out from expected destination hub |
| `POST /rider/tasks/{task}/deliver` | Multipart genuine proof, recipient evidence, exact COD acknowledgement |
| `POST /rider/tasks/{task}/fail` | Allowed reason, useful notes and required evidence; server increments attempt and instructs hub return |
| `GET /rider/commands/{idempotency_key}` | Reconcile an owned command after timeout/app restart without replaying a new intent |
| `GET /rider/trips` and `GET /rider/trips/{trip}` | Paginated scoped recorded history and checkpoints |
| `GET /rider/conversations` | Only currently authorized delivery/phase-linked threads |
| `GET /rider/conversations/{thread}/messages` | Bounded paginated messages, stable message IDs and display boundary |
| `POST /rider/conversations/{thread}/messages` | Plain text, explicit expected phase, no client-selected recipient |
| `POST /rider/conversations/{thread}/read` | Acknowledge through an actually displayed `last_seen_message_id` |
| `GET /rider/notifications` | Durable scoped notifications once backend phase is complete |
| `POST /rider/notifications/{notification}/read` | Idempotent own-notification acknowledgement |
| `GET /rider/cash` and `GET /rider/earnings` | Read-only server ledger/confirmed earnings, gated by financial readiness |
| `GET /rider/recovery` | Only explicit narrowly scoped recovery instructions for a restricted courier; separate policy |
| `GET /rider/proofs/{proof}` | Authenticated, scoped private proof retrieval with no-store response; no public filesystem path |
| `PATCH /rider/profile` | Only approved self-service contact fields using shared validation; managed placement/role/evidence stay read-only |
| `PUT /rider/password` | Current-password verification, shared password policy and other-device revocation decision |

`job`, `task`, and `trip` are API view references, not a requirement to add three
new database tables. Agree stable IDs derived from actual parcel/assignment
records. A phase-specific task reference must not grant both pickup and final-mile
permissions on the same delivery. Query collections remain scoped on every page.

There is no generic status update, self-approval, role conversion, hub intake,
manifest, retry scheduler, buyer-complete, seller-returned, or platform-reconcile
rider endpoint. Remittance submission/receipt commands require their own
backend financial contract; no invented transfer endpoint is added here.

## Authentication and access

Use Laravel Sanctum personal access tokens for the native client, with a device
label, explicit configured expiration, pruning, current-device logout, and a
reviewed revocation policy for password reset/suspension/account closure. Sanctum
tokens do not expire by default; this app must choose and test an expiration.
Start with reauthentication on expiry; do not invent a JWT refresh service.
[Sanctum mobile-token and expiration documentation](https://laravel.com/framework/docs/13.x/sanctum)
supports this approach.

Required backend work includes `HasApiTokens` and its persistence setup,
token issuance/revocation, `auth:sanctum` routing, API-aware positive account
policies, and tests. Token abilities narrow commands but never substitute for
fresh role, approval, active account, placement, ownership, or assignment checks.

Pending/rejected couriers may authenticate to **own holding data only** where
the existing account policy allows; suspended couriers receive only the defined
restricted/recovery capabilities. Wrong-role login must not grant rider access.
Inactive/restricted recovery token issuance is a policy decision, not a shortcut.
Reject unknown eligibility and fail closed for new work.

Browser first-party authentication retains secure session cookies/CSRF under
the existing web policy. Flutter web account interaction is limited to an explicitly enabled debug
loopback build with the synthetic local backend and memory-only bearer state.
Production first-party web authentication remains cookie/CSRF-based.
Never persist production bearer tokens in browser local storage to make preview
login easier. Native clients are not subject to browser CORS, but browser
previews require explicit allowed origins, credentials policy, and CSRF where
cookies are used. Do not solve either with a global wildcard.

Login/reset errors avoid account enumeration. Apply backend limits to normalized
identifier and trusted source, hide secrets from errors/logs, and revoke/check
tokens consistently across web and API access. Do not reuse a session-only
middleware that redirects an API request or assumes a browser session exists.

## Resource shape and disclosure

The server constructs allowlisted JSON Resources/DTOs instead of dumping Eloquent
models or Inertia props. A pickup preview has only authorized seller/stop details;
buyer contact, exact private destination and unrelated payment data are withheld.
Final-mile data appears only within the authorized assignment. Proof access and
KYC access have separate policies; general user JSON contains neither storage
paths nor public evidence URLs.

Synthetic task example; IDs/addresses are fixtures, not real people or records:

```json
{
  "data": {
    "id": "task_demo_final_01",
    "parcel_id": "parcel_demo_01",
    "phase": "final_mile",
    "stage": "out_for_delivery",
    "order_status": "OUT_FOR_DELIVERY",
    "tracking_number": "DEMO-WAYBILL-001",
    "next_stop": {
      "kind": "buyer_destination",
      "name": "Demo recipient",
      "address": "Example Street, Demo Barangay, Demo City",
      "coordinates": null
    },
    "cod_due": { "currency": "PHP", "minor_units": 125050 },
    "attempt_number": 1,
    "allowed_actions": ["deliver", "fail"],
    "blocked_actions": [],
    "updated_at": "2026-10-05T04:00:00Z"
  },
  "meta": { "request_id": "demo-request-01" }
}
```

The detail may supply a `version` for stale-input detection, minimal permitted
contact actions, immutable cash snapshot, recorded custody, failure code options,
and purpose-specific proof limits. These fields must be explicitly agreed, not
inferred from the example. `allowed_actions` is a UI hint, never authorization.
Do not default missing `cod_due` to zero/prepaid; require an explicit no-COD state.
Unknown action codes are unavailable until the client understands them.

Pagination links must stay on the approved API origin/path; a client cannot
follow an arbitrary response URL with its Authorization header. No response
may expose foreign identifiers merely to explain a permission failure.

## Command payloads and server validation

| Command | Proposed input | Server-derived/checked |
|---|---|---|
| Claim | Empty body, idempotency header | Actor, eligible company/hub/barangay, capacity, ready state, one winning assignment |
| Duty | `on_duty` boolean, no “toggle” instruction | Own account, allowed duty policy, fresh returned state |
| Pickup/depart | `waybill_code`, optional approved note, expected task version if supported | Normalization, exact match, assigned actor/phase, expected stop/source state |
| Deliver | `proof` file, recipient name or relationship under agreed rules, note if permitted, exact `collected_minor_units` for COD | Content type/size/dimensions, ownership, order amount, current custody, server time, one outcome |
| Fail | `reason_code`, meaningful notes, proof if reason requires it | Allowlisted reason, attempt count, authorized assignment, hub return instruction |
| Send message | `body`, `expected_phase`, idempotency header | Authorized thread/recipient, current phase, plain-text rules, one message |
| Read thread | `last_seen_message_id` | Message belongs to thread and was returned within authorized boundary |
| Release | `reason_code`, notes as required | Before collection only; reason policy, immutable audit, return to board |

Use the backend's normalized NFKC plain text, field lengths, Philippine phone,
identifier, and file rules. Read configured limits in `/rider/me`; the UI may
hint them, but Laravel validates again. File MIME comes from content, not the
extension. Reject extra privileged inputs such as rider/hub IDs, approval,
role, timestamps, order status, pricing, capacity, or attempt number.

Freeze upload MIME/byte/pixel limits, key retention, token expiry, reason codes,
recipient-evidence fields, page/filter enums, and password-device behavior
in the first contract review. Public docs must not invent an earnings rate or
pretend the legacy backend already enforces these proposed limits.

## Idempotency, locks, and uncertain results

Use a random UUID key per mutation intent, reused on retries. The server stores
a uniqueness-protected command record scoped to actor, action/route, key, and
canonical payload fingerprint. For files use a content hash; exclude changing
multipart boundaries and transport-only metadata from the fingerprint.

- Same completed intent returns its original safe result without new custody,
  proof, cash, message, or checkpoint events.
- Same key with different intent/input returns `409 IDEMPOTENCY_MISMATCH`.
- Concurrent matching requests cannot execute twice. The second returns the
  original result or `409 COMMAND_PENDING` with a refresh/reconciliation path.
- Business/command state and required events commit atomically. Recheck scope
  before replaying a stored result; lost permission cannot leak old private data.
- Scoped command lookup returns pending/succeeded/failed and safe result or
  failure information. Unknown owned key means no retained record, **not proof
  that a business event never happened**.

After a confirmed validation rejection, changing a field/file creates a new
intent and key. Retain the old key only for an unchanged retry/reconciliation.
Do not edit/re-key an outcome while its original result is still uncertain.

Retention proposal: at least seven days for command lookup/replay, subject to
backend agreement. Retain immutable business evidence longer under its policy.
An expired key must never replay a custody action blindly; current state and
natural actor/parcel/action/facility invariants still prevent duplicate outcomes.

Lock order before parcel consistently with existing services, then relevant
assignment/cash/command records in a documented order. Claim race/capacity
constraints require isolated PostgreSQL concurrency tests; SQLite cannot prove
row-lock behavior. Account/placement changes must be rechecked in transactions.

The client keeps a minimal pending-intent record when cross-restart recovery is
implemented: command key, own scoped task reference, action and expiry, stored
privately without proof/contact bodies. Its storage/cleanup is a separate tested
implementation item. With memory-only first slice, process loss requires a fresh
task/event read and explicit review before any new submission; do not claim
automatic crash recovery until the minimal pending-intent store exists.

## Proof upload lifecycle

Use one multipart outcome request initially, rather than a second public upload
service. Store the file privately, verify it, then commit its immutable reference
with the authoritative outcome and required event/cash record. Filesystem writes
are not rolled back by database transactions: on failure remove the new orphan,
and reconcile/delete abandoned uploads with a tested cleanup policy. Never
delete accepted evidence during a retry.

Return success only after file persistence and business commit succeed. A failed
storage write leaves status/custody/cash unchanged. A duplicate uses the original
stored proof; cleanup must not delete a file referenced by a committed result.
Enforce transport/proxy size limits consistently with server validation. Handle
timeouts as uncertain commits until command/task reconciliation confirms them.

Native drafts survive a normal field/network rejection in the current session.
Android picker recovery must handle process loss. Any on-disk draft feature needs
app-private storage, short retention, account binding, explicit removal on
logout/restriction, and no gallery/export leakage. Draft resilience is not an
offline delivery system. No new location permission or public photo URL is needed.

## Errors

The API always returns JSON for API routes, including auth/validation failures;
no Inertia redirect, HTML login screen, or infrastructure challenge page is
treated as success. Decode unexpected content as a transport/infrastructure
failure with a safe request reference.

| HTTP | Meaning | Client behavior |
|---|---|---|
| 401 | Missing, expired or revoked token | Clear private session state, require sign-in; do not loop retry |
| 403 | Known account/action forbidden | Explain restriction; refetch only permitted capabilities/recovery |
| 404 | Scoped record unavailable | No foreign details; remove/refresh stale selection |
| 409 | Stale source, already claimed, changed assignment, duplicate-key conflict | Reconcile/refetch authoritative state and permitted next action |
| 422 | Field validation | Inline errors, preserve safe draft and original intent |
| 429 | Rate limit | Respect `Retry-After`, avoid timer-driven retry storms |
| 413 | Request/upload too large | Explain actual configured limit and permit replacing proof |
| 5xx/timeout | Infrastructure failure or unknown command result | Safe reference, bounded backoff for reads; reconcile mutations |

Synthetic conflict example, limited to data this actor may still see:

```json
{
  "error": {
    "code": "STATE_CONFLICT",
    "message": "This task changed. Refresh to review its next step.",
    "fields": {},
    "current_state": "PICKED_UP",
    "allowed_actions": [],
    "request_id": "demo-request-02"
  }
}
```

Agree the finite machine-readable error catalogue alongside acceptance tests.
Use 403/404 without state detail after permission loss; conflict information
must not leak another rider's identity, contact, hub, proof, or cash history.

## Caching and compatibility

Private auth/task/contact/proof/cash responses use `Cache-Control: private,
no-store` and bypass CDN caching. Logs/error reports exclude tokens, raw bodies,
proof bytes, KYC paths, OTPs and contact information. Preserve normal authentication,
WAF/rate limits and explicit trusted proxy configuration.

Mobile releases outlive a backend deploy. Keep old v1 fields/semantics while
supported, add nullable fields/capabilities, and test an older client fixture
before deployment. Do not remove or reinterpret a field during a web-only
refactor. Contract ownership, rollout and rollback are defined in
[INTEGRATION_PLAN.md](INTEGRATION_PLAN.md).

Normative sources: [web validation](https://github.com/Auvryy/BagooPH/blob/main/docs/CORE_FLOW_VALIDATION_AND_EDGE_CASES.md)
