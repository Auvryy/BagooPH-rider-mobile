# Rider interaction and reliability audit — November 3, 2026

## Scope and interpretation

This audit checks the current Rider client and its compatibility with the
committed local web backend. Rider source started at `03942c2`; the reviewed
backend snapshot is `9e5c73b2fe9415f8444fc33a46f7808469c0d894`. The backend's
current version-two completion and retained-evidence rules govern newer orders.
The buyer application and other developers' changes are outside this audit.

Passing PC checks establish the behavior exercised by those checks. They do
not establish that Azure contains this source, that Android hardware behaves
the same way, or that every possible input or device has been tested. No
production parcel/payment writes, database reset, or deployment were performed.
All kernel scenarios use synthetic data in isolated SQLite `:memory:`. The
corrected native preview explicitly overrides authentication before any live
session restoration can occur.

## Build and verification priorities

1. **Keep recoverable interaction feedback complete.** The confirmed auth
   gaps are fixed here. Retain field-specific messages, announced summaries,
   clear pending states and duplicate protection in subsequent form changes.
2. **Accept the current backend/client pair before enabling more writes.**
   Deploy the reviewed source through the owning workflow, verify its APIs and
   migrations, and exercise one complete assignment/delivery/recovery scenario
   with approved test accounts. Existing independent deployment gates must not
   be cleared with fixture results. This audit does not deploy anything.
3. **Complete physical Android acceptance when a phone is available.** Cover
   camera denial/retry, GPS permission changes, picker cancellation/process
   death, offline/reconnect, background/resume privacy and retained-command
   recovery. Linux layouts cannot resolve these checks.
4. **Verify notifications and financial recovery with their owning actors.**
   Demonstrate durable notices, scoped message reads, hub COD receipt and
   reconciliation without confusing them with delivery completion or earnings.
   Keep in-app inbox evidence distinct from OS push acceptance.
5. **Finish release and representative performance checks.** Verify the
   approved package/signing identity, native memory/battery/thermal behavior,
   realistic upload sizes and a controlled staging load. A synthetic tile
   benchmark does not prove phone or production performance.

The present evidence supports fixing the identified feedback defects and
continuing integration/device acceptance. It does not justify adding optional
features ahead of unresolved custody, authorization, proof and cash gates.
